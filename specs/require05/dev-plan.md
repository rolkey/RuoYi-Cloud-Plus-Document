# 实时信息通道开发计划

> 配套文档：`requirement.md`（需求）、`plan.md`（架构与实施方案）
> 开发原则：按 `plan.md` 从零搭建 `ruoyi-websocket` 模块，不依赖既有程序细节

---

## 一、概述

本计划基于 `plan.md` 的三阶段方案（后端基础设施 → 业务侧接入 → 前端接入），将每个阶段拆分为可独立交付、可验收的任务，明确依赖关系、工作量估算与里程碑，作为开发排期与进度跟踪依据。

---

## 二、开发范围

**在范围内：**

1. 新建 `ruoyi-websocket` 服务模块（会话管理、三级订阅、MQ 消费、WebSocket 推送）
2. 三级主题订阅（主类/子类/具体业务ID）+ 前缀匹配路由
3. 业务侧发布封装（`WebSocketUtils` / `WebSocketTopicUtils` / `WebSocketTopic`）
4. 订阅/退订/查询 REST 接口
5. 前端主应用 WebSocket 客户端 + 订阅接口封装 + 消息总线派发
6. HIS 子应用接入示例

**不在范围内（本期不做）：**

- 不修改既有业务模块核心逻辑（仅在触发点增加推送调用）
- 消息持久化 / 离线补发 / 历史消息查询
- 点对点 IM 的已读、回执、撤回等高级能力
- 消息幂等去重的业务级保障（仅做连接层去重）

## 三、任务分解（WBS）

### Phase 1：后端基础设施（预估 7 人日）

| 任务编号 | 任务 | 交付物 | 依赖 | 预估 |
|----------|------|--------|------|------|
| T1.1 | 模块骨架 | 模块目录 + `pom.xml` + 父 pom 注册 + `application.yml` 骨架 | 无 | 0.5 人日 |
| T1.2 | 主题工具 | `WebSocketTopicUtils`（build/split/validate/prefixes）+ `WebSocketTopic` 常量 | T1.1 | 0.5 人日 |
| T1.3 | 会话管理 | `WebSocketSession` + `WebSocketSessionService` + `PlusWebSocketSessionService` | T1.1 | 1 人日 |
| T1.4 | 端点与鉴权 | `WebSocketEndpoint`（@OnOpen/@OnClose/@OnError/@OnMessage）+ token 校验 + 心跳 | T1.3 | 1 人日 |
| T1.5 | 订阅管理 | `WebSocketSubscribeService` + `WebSocketSubscribeController`（订阅/退订/查询） | T1.2、T1.3 | 1.5 人日 |
| T1.6 | MQ 生产/消费 | `WebSocketMessageDto` + `WebSocketUtils` + `WebSocketConsumer`（前缀匹配路由） | T1.2、T1.3、T1.5 | 1.5 人日 |
| T1.7 | 配置与联调 | 完整 `application.yml`（MQ 交换机/队列、Redis、心跳超时）+ 本地启动自测 | T1.6 | 1 人日 |

**Phase 1 验收标准（M1）：** 服务可启动；客户端可建立 WebSocket 连接并完成鉴权；可通过 REST 订阅/退订；MQ 消息能按三级前缀匹配推送到目标客户端。

### Phase 2：业务侧接入（预估 1 人日）

| 任务编号 | 任务 | 交付物 | 依赖 | 预估 |
|----------|------|--------|------|------|
| T2.1 | 打通示例链路 | 在 system 通知业务触发点调用 `WebSocketUtils.publishMessage`，端到端推送验证 | Phase 1 | 1 人日 |

**Phase 2 验收标准（M2）：** 业务服务产生事件 → 经 MQ → websocket 模块 → 推送到已订阅客户端，全链路日志可追踪。

### Phase 3：前端接入（预估 4 人日）

| 任务编号 | 任务 | 交付物 | 依赖 | 预估 |
|----------|------|--------|------|------|
| T3.1 | 主应用 WebSocket 客户端 | `src/utils/websocket.ts`（建连/心跳/重连/收发单例） | Phase 1 | 1 人日 |
| T3.2 | 订阅接口封装 | `src/api/websocket/index.ts`（subscribe/unsubscribe/查询） | T3.1 | 0.5 人日 |
| T3.3 | 消息总线派发 | 主应用 onmessage → 按 `type` 派发到 mitt；监听子应用上送 | T3.1 | 1 人日 |
| T3.4 | 子应用接入 + 登录集成 | 登录后生成 clientKey 建连 + 初始订阅；HIS 订阅 `his/*` 示例 | T3.1、T3.2、T3.3 | 1.5 人日 |

**Phase 3 验收标准（M3）：** 主应用单连接复用；服务端推送能经总线到达对应子应用；断线可自动重连并重新订阅；HIS 子应用能收到 `his/*` 推送。

## 四、里程碑与排期

| 里程碑 | 完成标志 | 预估累计 | 验收口径 |
|--------|----------|----------|----------|
| M1 后端可连接 | Phase 1 完成 | 7 人日 | 服务启动、连接/订阅/MQ 推送闭环 |
| M2 端到端打通 | Phase 2 完成 | 8 人日 | 业务事件 → 客户端推送全链路可追踪 |
| M3 前端接入完成 | Phase 3 完成 | 12 人日 | 主应用单连接 + 总线派发 + 子应用可接收 |

> 说明：Phase 2 与 Phase 3 可并行（后端打通示例链路的同时，前端搭连接与订阅）。

## 七、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 多实例会话/订阅一致性问题 | 推送丢失 | 会话与订阅强制落 Redis，多实例联调纳入 M1 验收 |
| 前缀匹配边界误判（`his/order` 匹配 `his/orderX`） | 错发消息 | `WebSocketTopicUtils.prefixes` 按段拆分，单测覆盖边界用例 |
| 断线重连后订阅丢失 | 客户端收不到推送 | 前端重连后强制重新订阅，纳入 M3 验收 |
| MQ 消息堆积/竞争消费 | 推送延迟、乱序 | 必要时按主类（模块）分队列，监控队列深度 |
| 与既有消息总线事件命名冲突 | 事件串扰 | 统一 `ws:{type}` 命名，接入前盘点现有 mitt 事件 |

## 八、开发规范约束

- 主题统一由 `WebSocketTopicUtils` / `WebSocketTopic` 常量生成，禁止业务侧手写字符串拼接。
- 禁止类型逃逸（`as any` / `@ts-ignore` / `@SuppressWarnings` 掩盖类型问题）。
- 所有模块改动需通过编译与静态检查，接口变更同步更新本计划与 `plan.md`。
- 提交粒度与代码库既有规范保持一致，非必要不引入新依赖。
