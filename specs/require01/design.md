# 设计文档

**状态**: 已批准
**版本**: 1.2.0
**最后更新**: 2026-05-04
**关联需求**: RQ-001

## 概述

* 当前项目是微服务架构，服务端在 RuoYi-Cloud-Plus 目录
* 前端为微前端架构，主应用与涉及核心的管理模块登录/人员管理等功能在 RuoYi-Cloud-Plus-UI 目录
* 计划根据需求做功能完善，不修改原有体系与结构

## 需求分析

### RQ-001-001：人员要有多个科室的权力

**需求描述：** 原有系统中，`sys_user` 表有 `dept_id` 字段，表示用户所属的科室（部门）。现在要求一个用户可以有多个科室的权力，原有结构不变，只是增加了跨科室的权力。

**现有系统分析：**

- `sys_user` 表通过 `dept_id` 字段（bigint，可空）记录用户的**主属科室**
- `sys_dept` 表是科室（部门）的主表，树形结构（`parent_id` + `ancestors` 祖级列表）
- 系统中已有类似的多对多关联模式：`sys_user_role`（用户-角色）、`sys_user_post`（用户-岗位）、`sys_role_dept`（角色-部门）
- 用户当前只能归属于一个科室（`dept_id`），无法跨科室操作数据

## 设计方案

### 方案一：新增用户-科室关联表（推荐）

**思路：** 沿用系统中已有的多对多关联模式（如 `sys_user_role`、`sys_user_post`），新增一张 `sys_user_dept` 关联表，记录用户与科室的额外关联关系。

**新增表结构：**

```sql
-- 用户与科室关联表（用于跨科室权限）
CREATE TABLE `sys_user_dept` (
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `dept_id` bigint NOT NULL COMMENT '部门ID',
  PRIMARY KEY (`user_id`,`dept_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户与部门关联表';
```

**逻辑说明：**

1. `sys_user.dept_id` 保持不变，仍表示用户的**主属科室**
2. `sys_user_dept` 表记录用户额外拥有的**跨科室权限**
3. 查询用户有权限的科室时：主属科室（`sys_user.dept_id`）+ 关联科室（`sys_user_dept`）
4. 数据权限过滤时，用户可访问的科室范围 = 主属科室及其子科室 + 关联科室及其子科室

**影响范围：**

| 模块 | 影响 | 变更说明 |
|------|------|----------|
| 数据库 | 新增 `sys_user_dept` 表 | 无存量数据迁移 |
| 后端 Entity | 新增 `SysUserDept` 实体 | 沿用 `sys_user_role` 模式 |
| 后端 Service | 新增跨科室查询逻辑 | 数据权限过滤时合并主属+关联科室 |
| 后端 API | 新增关联科室增删接口 | 或复用人编辑接口扩展 |
| 前端 | 用户编辑页增加"关联科室"多选 | 沿用岗位/角色选择组件模式 |

### 方案二：扩展 dept_id 为多值字段（不推荐）

**思路：** 将 `dept_id` 改为存储多个科室 ID（如 JSON 数组或逗号分隔）。

**缺点：**
- 破坏原有 `dept_id` 的单值语义，影响范围大
- 关联查询无法使用索引，性能差
- 与系统中大量基于 `dept_id` 的查询逻辑不兼容
- 不符合数据库设计范式

### 方案对比

| 维度 | 方案一（关联表） | 方案二（多值字段） |
|------|-----------------|-------------------|
| 对现有系统影响 | 小，新增表不影响现有逻辑 | 大，需修改大量查询逻辑 |
| 查询性能 | 好，可利用索引 JOIN | 差，无法使用索引 |
| 扩展性 | 好，易于扩展 | 差，字段长度受限 |
| 实现复杂度 | 低，复用现有模式 | 高，需改造数据权限层 |
| 数据一致性 | 好，外键约束 | 差，字符串解析易出错 |

**结论：采用方案一。**

## 数据权限设计

### 当前数据权限模型

Ruoyi 的数据权限通过 `DataScope` 注解 + `dept_id` 过滤实现，主要级别：

- **仅本人**：`user_id = 当前用户`
- **本部门及以下**：`dept_id IN (当前部门及其子部门)`
- **本部门**：`dept_id = 当前部门`
- **自定义**：根据 `sys_role_dept` 表

### 改造方案

在数据权限过滤时，将用户的"可访问科室列表"扩展为：

```
可访问科室 = 主属科室(dept_id) ∪ 关联科室(sys_user_dept)
```

具体改造点：

1. **数据权限拦截器**（`DataScopeInterceptor` 或类似 AOP）：在拼接 SQL 时，将 `dept_id` 过滤条件扩展为包含关联科室
2. **用户上下文**（`LoginUser`）：增加 `deptIds` 字段，缓存用户所有可访问科室 ID 列表
3. **用户切换科室**：前端可提供科室切换功能，当前活跃科室决定"本部门"类数据权限的具体值

## 前端设计

### 用户编辑页扩展

在用户编辑/新增页面中，增加"关联科室"多选组件：

- 位置：在"归属科室"（主属科室）下方
- 组件：使用 `el-tree-select` 或 `el-select` 多选，与现有角色选择组件风格一致
- 数据：加载全部科室树，已选中的主属科室默认勾选且不可取消（或灰显提示）
- 交互：支持搜索过滤科室

### 科室切换

在用户头像/个人信息下拉菜单中增加"切换科室"功能：

- 显示当前用户有权限的所有科室列表
- 切换后更新当前活跃科室，影响数据权限过滤范围
- 默认活跃科室 = 主属科室

## 接口设计

### 后端 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/system/user/{userId}/depts` | 获取用户关联科室列表 |
| PUT | `/system/user/{userId}/depts` | 更新用户关联科室（全量替换） |
| GET | `/system/user/myDepts` | 获取当前用户所有可访问科室 |

### 数据权限接口扩展

在现有数据权限工具类中增加方法：

```java
// 获取用户所有可访问科室ID（主属 + 关联）
List<Long> getAccessibleDeptIds(Long userId);

// 判断用户是否有某科室的访问权限
boolean hasDeptAccess(Long userId, Long deptId);
```

## 数据迁移

无需数据迁移。新增 `sys_user_dept` 表为空表，存量用户的 `dept_id` 保持不变。

## 未解决的问题 / 待讨论

1. **科室切换后的 UI 状态**：切换科室后，菜单权限、首页数据是否需要随之变化？
2. **数据权限层级**：关联科室是否也遵循"本部门及以下"的树形展开逻辑？即关联了分院，是否自动拥有其子科室权限？
3. **批量操作**：是否需要支持批量给用户赋予关联科室？
4. **与租户的关系**：关联科室是否跨租户？目前看不需要，关联科室应在同一租户内。
